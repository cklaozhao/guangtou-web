# SRD — 个人门户主题库（光头 Obsidian 教程门户）

> Version: V0.1
> Date: 2026-05-02
> Author: Saibo（自用文档）

## 1. Customer

本项目为**自用 + 兴趣驱动**的开源静态门户，没有商业化目标，但目标使用者画像清晰：

- **知识博主**：在飞书 / Notion 写公开内容，需要一个对外可分享的入口
- **自由职业者**：希望有一个能放在简介里的"个人主页"，但不想为此购买独立产品
- **个人品牌开发者**：想要一个能体现审美的 landing page，作为对外名片

**第一受众是作者本人**——任何一版主题首先要满足作者自己想用、想换。

## 2. Job to be Done

> 让有飞书 / Notion 文档的人，**用一个静态 HTML 文件**就能拥有一个跳转到自己文档的个人门户主页，**无需购买第三方产品、无需折腾域名**——直接丢进自己的博客就能部署。

## 3. Benefit

### 3.1 客户价值和收益

- **零成本**：不需要购买 landing page 类 SaaS（typedream / framer 等），不需要单独申请域名
- **零运维**：单文件 HTML，部署即用，没有数据库、没有后端
- **审美红利**：每一版主题都是从社交平台已被验证的爆款 UI 复刻而来，拿来即拥有"高级感"
- **可换可丢**：哪天想换主题，直接换一个 HTML 文件即可，迁移成本接近零

### 3.2 业务价值和收益

无商业指标。软性价值：

- **作品集**：每一版主题都是一次"复刻 + 整合"练习，沉淀作者审美与前端能力
- **开源潜力**：如果某一版主题恰好戳中需求，有机会成为受欢迎的开源主题库（非首要目标）

## 4. Problem

想拥有一个"看起来不糟糕"的个人门户/主页，目前社区的解法都有摩擦：

| 现有方案 | 痛点 |
|---|---|
| 买 typedream / framer / carrd 等 SaaS | 月费 + 自定义受限 + 数据被锁在第三方 |
| 自己买域名 + 部署 Hugo / Astro | 域名年费 + 需要懂前端 + 改主题成本不低 |
| 直接用飞书/Notion 的公开链接当门户 | URL 又长又丑、品牌感为零、没法做交互 |
| 用 GitHub Pages 默认主题 | 套娃感强、主题千篇一律 |

**核心诉求**：用户其实只是要一个"漂亮的跳转中转站"，但市面上的方案都把它做重了。

## 5. Solution

一个**单文件 HTML 静态门户主题库**——主项目骨架已成型（hero + canvas glitch 背景 + 头像交互 + 标题 + 跳转链接 + 备案区），后续以"多主题"形式持续扩展。

每一版主题作为一个独立的 HTML 文件沉淀进项目，使用者按喜好挑选，丢进自己的博客即可部署。

### 5.1 Benchmark Analysis（标杆分析）

主题来源策略不是"自己拍脑袋设计"，而是**外包给社交平台的流量数据**：

- **筛选源**：小红书、YouTube、X 上点赞 / 浏览量明显高于均值的 UI 设计 / 网站
- **筛选逻辑**：流量高 = 已被市场验证 = 复刻方向不会错
- **复刻方式**：让 Claude Code 帮助 1:1 复刻关键交互，再整合成本项目的主题文件
- **优势**：把"什么是好看"这个主观问题，转化成"什么是受欢迎"的客观信号，避免审美内耗

### 5.2 Before/After Comparison（前后对比）

| 维度 | Before（现状） | After（目标） |
|---|---|---|
| 项目形态 | 一个已成型的 hero 页（v2.2）| 一个主题库，N 个风格各异的 HTML 文件 |
| 主题来源 | 作者单点开发 | 社交平台爆款驱动的复刻流水线 |
| 用户选择 | 只能用当前一个版本 | 按场景/审美挑主题，像换皮肤 |
| 迭代节奏 | 单版本细节打磨 | 每见到一个想复刻的就开一个新主题 |

### 5.3 Scope（In / Out）

| In Scope（本期范围） | Out of Scope（不在本期） |
|---|---|
| 单文件 HTML，自包含 CSS/JS | 多页应用、路由、构建工具链 |
| 静态门户 + 跳转外链（飞书/Notion） | 内嵌渲染飞书/Notion 内容、API 调用 |
| 多主题（每个主题独立 HTML 文件） | 主题切换器、运行时换肤 |
| 复刻爆款 UI / 交互 | 原创设计语言体系 |
| 自用 + 朋友零摩擦取用 | 多语言、SEO、分析埋点、商业化 |
| 桌面端体验为主 | 严格的移动端适配（Phase N+ 再考虑） |

| 阶段 | 范围 | 目标 | 依赖 |
|---|---|---|---|
| Phase 1（已完成） | `guangtou.html` v2.2 — hero + canvas glitch + 头像 mask 交互 | 跑通主项目骨架，验证"单文件门户"形态 | 无 |
| Phase 2（下一步） | 模仿 **反重力（Antigravity）官网**的交互界面，复刻成新主题 | 验证"复刻流水线"是否顺畅 | Phase 1 骨架 |
| Phase 3（候选） | **极简风**主题 | 提供给不喜欢重交互的用户 | 复刻流水线已跑通 |

## 6. Success Metrics

本项目**有意不在自身设量化指标**——成功信号已经在选题阶段被前置筛选：

| 指标类型 | 指标名称 | 目标值 |
|---|---|---|
| 核心指标（前置） | 复刻源在小红书/YouTube 的点赞 / 浏览量 | 明显高于同类内容均值（凭手感判断） |
| 观测指标 | 作者本人是否真的把它换成自己博客的当前主题 | 至少有 1 版主题进入"在用"状态 |
| 软性指标 | 朋友 / 陌生人是否拿去部署 | 有就更好，没有也不影响项目继续 |

> 设计哲学：**不在自己项目设 KPI，把"对不对"的判断外包给已经被流量验证的源素材。**

## 9. Product Requirements

后续每个主题统一遵循以下底线（避免主题数量增长后失控）：

- **单文件交付**：HTML + 内联 CSS + 内联 JS，资源走 CDN 或 base64
- **零依赖部署**：扔进任何静态托管（博客、GitHub Pages、Cloudflare Pages）即用
- **门户语义不变**：每个主题都至少包含 hero + 跳转链接区 + 备案区三个部分
- **可读性**：注释 + 关键交互的 GOTCHA 写进 `CLAUDE.md`，方便自己一年后还看得懂

## 10. UI/UX Requirements

主题级 UI/UX 由各主题各自定义，但库级别有统一约束：

- **跳转优先**：再炫的交互也不能干扰"点击 → 跳到飞书/Notion"这个核心动作
- **加载即可见**：单文件部署不允许长加载态，首屏关键元素需要立即可见
- **桌面端为主**：复刻的 UI 多为桌面端审美，移动端做基本可用即可
- **无障碍底线**：链接要是真链接（`<a href>`），不要为了酷炫把跳转做成 onclick JS（影响外链 SEO 与新标签页打开）

> 单个主题的详细 UI/UX 规格在该主题对应的 PRD（如有）中展开。
