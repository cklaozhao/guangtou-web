光头 Obsidian 教程落地页开发总结 & 新人手册

如果你只有 5 分钟，请直接跳到 第 4 节。

01项目速览

这是一个单文件 HTML 落地页，作为「光头 Obsidian 教程」飞书 wiki 的入口页。整页只有一屏 hero section + 底部备案条，但视觉/交互上做了不少事：

  • 背景：canvas 字符矩阵滚动（"glitch" 风格）
  • 头像：双层 —— 顶层是远端线条画，底层是真人照，鼠标进出时切换显示
  • cursor-ring：自定义鼠标光圈，跟随 + mix-blend-mode: difference（颜色反色）
  • 标题：打字机动画 + hover 下划线展开
文件说明
guangtou.html唯一会编辑的产出文件。约 125KB，HTML + CSS + JS + 内嵌 base64 真人照都在一个文件里
头像.jpg真人照原图（1528×1526），已被压缩 + base64 嵌入 html，原图作备份
源码.html参考源码（小米 MiMo 100T Hero 复刻）。不要直接改它，仅作为 cursor-ring / glitch canvas 的对照
CLAUDE.md项目协作约定 + 术语对齐表 + 状态机表 + GOTCHA 列表。每次开始工作前先读它
远端 URL顶层线条头像图（在 cos 图床），被 .logo::after 引用。换头像要去 cos 改

仓库：github.com/cklaozhao/guangtou-web

02开发时间线（6 次迭代）

每次都是一个目标明确的小迭代，分支命名 logo-N，做完 fast-forward merge 回 main 再开下一个。看这条时间线能很快感受到这个项目的"绕路"在哪。

  1. init · 82c4817
    项目初始化备份。已包含基础视觉（hero / 头像双层 / 字符矩阵 / cursor-ring 跟随 + difference）
  2. logo-1 · b4d54f9 · 头像上的"双圈"问题
    用户发现鼠标在头像上时同时出现两个圆形：内圈 40px 反色 disc + 外圈 80px 线条揭示。决定保留外圈、隐藏内圈。改动：.cursor-ring.is-on-logo 加 visibility: hidden（1 行）
  3. logo-2 v1 · ea9b5a3 · 进入头像加渐进过渡（割裂版）
    原本鼠标进头像时底层瞬间显示，希望加扩散过渡。第一版用 RAF 驱动 reveal-size 从 100→maxR (350ms)，结束后才切 inverted mask 露出小窗 —— 但用户说"先扩散→才出现小窗"是割裂的
  4. logo-2 v2 · a955cbc · 单一参数化 mask
    把"默认 mask + .is-inverted 反向 mask"两套合并成一套带 5-stop 的 radial-gradient。inner-r 控制小窗、outer-r 控制底层环带外径。进入头像 inner-r 瞬切 0→40，outer-r 同时缓动 100→maxR——扩散和小窗同时进行
  5. logo-3 · fa9d309 · 减速 + 字上光圈尺寸
    用户反馈 350ms 扩散仍太快"人眼跟不上"，调到 800ms。同时 .cursor-ring.is-hidden 从 16px 改 40px
  6. e45a2da · 修复文字反转圆圈大小（用户手动）
    用户验证 logo-3 后觉得字上 40px 还是不够大，自己直接编辑 1 个数字把 .cursor-ring.is-hidden 改成 100px 并 commit。这恰好印证了项目的"模块化设计哲学"——感官参数集中成单个常量后，用户自己也能改

03典型绕路案例

挑 3 个最有代表性的"绕路"，让你感受为什么这些工作量看起来超出"小调整"的预期。

案例 A · 同一个词「反转」指两件事

用户说"我要保留非反转的那个"。乍看意图明确，但代码里存在两个独立的"反转"语义：

  1. 颜色反转 = mix-blend-mode: difference（cursor-ring 用了它，所以鼠标圆圈是反色的）
  2. 遮罩反转 = 当时的 .logo.is-inverted::after 这套类（mask radial-gradient 的方向反向）

用户视觉上看到的"两个圆环"，其实分别对应这两件事：内圈是颜色反转的 disc，外圈是遮罩反转产生的揭示区。当用户说"非反转"，TA 指的是没有用 mix-blend-mode 处理的那一个——但 AI 单凭文字两种解释都成立。

教训：同一个中文词在代码里指多个独立概念时，必须主动建立术语表。我们用 CLAUDE.md 的"中英术语对齐"段沉淀这个对齐 —— 一旦写下"用户说 X = 代码里 Y"，下次会议就不再有歧义。

案例 B · 串行动画的"卡顿感"

logo-2 v1 实现了：先扩散 350ms，扩散完才切 inverted mask 露出小窗。从代码看是两阶段顺承，从用户视角看是"前面在扩散→突然多了个小窗"两件事先后发生。用户反馈"非常割裂"。

真正的解法不是调时长，而是把视觉模型改了：原来 mask 是"单半径圆"在两套规则间切换，现在 mask 是"双半径环带"在一套公式里参数化。两个动画变量（inner-r 瞬切 + outer-r 缓动）在同一帧里联动 —— 时间上不再是串行而是同步。

教训：如果用户说"割裂 / 卡 / 不连贯"，不要去调动画曲线，要回头看视觉模型是否本身有"两件不同的事在切换"。能用一套参数化模型表达的视觉，就别用"两套规则切换"做。

案例 C · "感官参数"的 AI 默认值经常偏小

同一种"开发觉得刚好、用户觉得不够"的偏差，在这个项目里出现了至少 3 次：

参数AI 初次给值用户调整到差异
扩散动画时长350ms800ms2.3×
字上 cursor-ring 尺寸40px（logo-3 改）100px（用户手动）2.5×
扩散动画时长（如果当初按 industry 中位）500ms800ms1.6×

开发自己写动画时大多落在 200-400ms（"功能反馈"区间），但展示性 / 教学性的动画用户希望看清过程，落在 600-1000ms。尺寸也类似 —— 开发觉得 "够用就行"，用户更看重 "存在感 / 视觉重量"。

教训：感官参数（时长 / 尺寸 / 不透明度 / 间距）AI 的"建议值"和用户期望经常 differ，提前告诉用户这是个易调常量（"如果觉得不合适只改这一个数字"），让用户可以低成本自己调而不是等下一轮迭代。

★04不知道一个东西叫什么时怎么办

这一节是这份手册的核心。下面 10 条全是我们在这个项目里实际验证过的方法 —— 它们让"用户用大白话提需求 → AI 写出对的代码"这条路尽量短。

  1. 用「行为 + 位置 + 时间」描述，不要追求精确名词

    不会说 "radial-gradient mask" 没关系。描述鼠标周围有一圈，圈内的颜色和外面是反的，鼠标到哪它跟到哪——AI 会还原成正确的技术词。

    实例："让鼠标移到头像上时，原来的真人照不要瞬间出现，要从我鼠标位置开始一圈一圈扩散过来。" —— 这一句完全没有用任何 CSS / mask 术语，但足够清晰，logo-2 v2 的整套方案就是从这一句长出来的。
  2. 用「对比」描述变化，不要直接给数字

    不要："改成 800ms"。要："现在太快了我人眼跟不上，慢一点，能让我看清扩散过程就行。" AI 会给一个建议值 + 解释 trade-off，你拍板。

    除非你已经精确知道自己要什么（"颜色 #f5f1e8" / "font-size 18px"），否则给目标体感比给数字有效得多 —— 因为感官值的 AI 默认普遍偏小（见上文案例 C）。

  3. 把效果拆成「状态」

    视觉效果 99% 是状态机。鼠标在 X 处时是 A 样，移到 Y 处时是 B 样，离开时是 C 样。直接拿"状态 → 视觉"的列表交给 AI：

    鼠标在 hero 空白处 → 跟随圆圈，碰头像边缘有硬边
鼠标在头像上     → 头像变底层，鼠标处一个小窗露线条
鼠标在标题上     → 圆圈缩小，颜色还是反的

    项目 CLAUDE.md 的"交互状态机"就是这种风格。表格写出来后，bug 通常是表格里某一格不对，定位很快。

  4. 描述时间顺序，标记「卡顿点」

    当感觉"哪里不对"时，把时间序列写清楚，标记不对的那一帧。例："先 A → 然后 B → 我觉得 B 出现得太突然，应该和 A 一起进行"。

    项目里"扩散和小窗割裂"的反馈就是这个模式 —— 用户没用任何技术词，只说"先后"和"卡"，足够让 AI 重做模型。

  5. 让 AI 起名字 + 维护术语表

    遇到"我说不上来"的东西时，描述完后加一句"这个东西在代码里叫什么？以后我用什么名字好"。让 AI 把对齐结果写进 CLAUDE.md。

    这份术语表是每次新对话 AI 都会先读的，相当于和未来的自己 / 同事 / 别的 AI 提前对齐。下次说"圆环"就不再歧义。

  6. 用熟悉世界打比方

    "像水墨晕开"、"像快门一闪"、"像窗帘拉开"、"像探照灯扫过" —— 非技术比喻能精准传递物理感。

    AI 会把比喻反编码成 easing 曲线 / 透明度 / 几何图形。比方比形容词（"自然一点"、"流畅一点"）有用得多。

  7. 说不上来时直接说「不知道」

    "我想要 X 体验，但不知道用什么实现，给我 2-3 个方案，告诉我各自的代价" —— 这一句能直接把决策权切回 AI，避免用错术语指错方向。

    AI 给的方案如果都不像，再具体说哪不像（"方案 1 那个圆从中间开始，但我希望从我鼠标已经画过的位置开始"），不要 just 说"不对"。

  8. 大改动先方案后动手

    需求一句话讲完，让 AI 出方案 + 状态表 + 改哪些文件。你看完再点头让动手。

    选择标准：会不会改超过 1 个地方。会改多处的、动到状态机的、动到视觉模型的，必须先方案。单一数字 / 颜色 / 类名直接改。

  9. 一次只改一件事

    不要："想加个 X + 改颜色 + 加按钮 + 让 Y 变快。" 每次只描述一个目标，验证完再开下一个。

    多任务一起提的副作用：(1) 方案变得很大没法 review，(2) 调错了一个不知道是哪个，(3) commit 难拆，回滚困难。

  10. 每次实施完，浏览器跑一遍

    类型检查 / 测试通过 ≠ 视觉对。HTML/CSS/JS 改动一定要打开浏览器把所有相关状态都跑一遍（这个项目的 6 个状态见 CLAUDE.md 的"验证"段）。

    项目约定每次实施完都要 commit + push —— 这样部署和浏览器测试可以同时进行，工作不会丢。

速查：提示词模板

当你想新加一个视觉/交互需求时，可以直接套这个模板（无脑填空）：

【现状】当前 [位置/状态] 的表现是 [描述视觉]。
【目标】我希望它变成 [描述视觉]。
【感受】我现在觉得 [太快/太慢/不连贯/突兀/不够明显/...]，
       希望 [更自然/更慢/更同步/更明显/...]。
【约束】保持 [其他状态/其他元素] 不变。
【请你做的】先给我方案 + 改哪些文件，等我点头再动手。
提示：这个项目的所有"先方案后动手"协作都是这种格式 —— 用户经常省略其中几格（比如"约束"很常省），AI 会自己回头问。所以即使填不全也无妨。

06推荐工作流

  1. 每次开新需求：先读 CLAUDE.md（术语表 + 状态机 + GOTCHA），不要靠记忆
  2. 判断改动量：单一数字 / 颜色 / 类名直接改；多文件 / 涉及状态机 / 涉及视觉模型 → 先讲方案
  3. 方案模式：让 AI 先输出方案（含改哪些文件、改后状态表、风险），点头再动手
  4. 实施后：浏览器开 guangtou.html，按 CLAUDE.md "验证"段跑全部状态
  5. commit + push：中文 commit message，前缀用 fix: / feat: / refactor: / tweak:。落定后立即推 origin（项目约定）
  6. 分支策略：每个迭代一个分支（logo-1、logo-2、logo-3...），完成后 fast-forward merge 回 main 并 push
  7. 同步文档：改动到了术语 / 状态机 / 视觉模型层面，记得回去改 CLAUDE.md，否则下次又要重新对齐
注意：不要 --no-verify 跳过 git hook、不要 git push --force 到 main、不要在没确认的情况下删分支。这个项目目前没配 hook，但保持习惯。

07第一天上手 checklist

  1. git clone github.com/cklaozhao/guangtou-web
  2. 读 CLAUDE.md（5 分钟，必须）
  3. 浏览器双击 guangtou.html，把鼠标依次移到：hero 空白 → 头像 → 标题 → footer 链接 → 移出窗口。每个状态对照 CLAUDE.md "验证"段确认行为
  4. 跑 git log --oneline，看完所有 commit 都做了什么
  5. 读这份手册的 §3（典型案例）和 §4（描述方法论）
  6. 让 AI（Claude Code 或别的）按 §4 模板提一个小改动（比如把 cursor-ring 颜色从 cream 改成别的），跑通"提需求 → 方案 → 实施 → push"整个流程
  7. 遇到第一个 GOTCHA 时回到 §5 速查 + CLAUDE.md GOTCHA 段
遇到任何"我不知道叫什么"的瞬间，立即回到 §4。这个项目能成的关键不是技术多复杂，而是不会描述也能描述这件事被打通了。
